# Цифровой деканат будущего МГИМО

Рабочий конкурсный прототип личного кабинета студента: расписание, БРС, заявки и справки, уведомления, цифровой студенческий билет и ИИ-ассистент. Интерфейс рассчитан на телефон от 360 px и сохраняет визуальное направление исходной версии проекта.

На сайте используются только вымышленные данные. Это концепт для конкурса, а не официальный сервис МГИМО.

## Что можно показать жюри

- вход по корпоративной почте, СНИЛС или телефону;
- два независимых студенческих сценария: отличник и студент с академической задолженностью;
- расписание на неделю с переносами и аудиториями;
- оценки БРС, GPA и прогноз академического результата;
- создание заявки на справку с отображением статуса;
- уведомления деканата и отметка прочтения;
- ИИ-ассистент с предложением действия, например оформления справки;
- профиль с цифровым пропуском и маскированием персональных данных.

## Архитектура безопасности

- `POST /api/auth` проверяет логин и пароль на сервере.
- Пароли сравниваются через `scrypt` с постоянным временем сравнения.
- После входа сервер выдаёт подписанную сессию в `HttpOnly`, `SameSite=Lax` cookie. В продакшене cookie получает флаг `Secure`.
- Профиль, расписание, оценки, заявки и уведомления выбираются по идентификатору из серверной сессии.
- Данные заявки хранятся в зашифрованной cookie состояния прототипа, поэтому они переживают обновление страницы и не доступны JavaScript напрямую. Для промышленной версии это место заменяется СУБД.
- `/api/chat` больше не принимает профиль студента от браузера: сервер сам получает текущий аккаунт из сессии и передаёт ассистенту только учебный контекст.
- В интерфейсе нет переключателя на другой аккаунт и клиентского режима деканата.
- Ключи задаются переменными окружения и не попадают в репозиторий.
- Vercel получает защитные заголовки: CSP, `X-Frame-Options`, `nosniff`, политика Referrer и Permissions Policy.

Прототип показывает безопасный пользовательский сценарий для конкурса. Перед промышленным запуском нужны полноценная СУБД, серверное хранилище заявок, управление ролями сотрудников, аудит и отдельный канал доставки второго фактора.

## Технологический стек

- React 19, TypeScript, Vite 8.
- Tailwind CSS 4, Framer Motion, lucide-react, шрифт Onest.
- Vercel Functions: `api/auth.ts`, `api/student.ts`, `api/chat.ts`.
- Node `crypto`: AES-GCM для состояния, HMAC для сессии, scrypt для паролей.
- Express-прокси для локального запуска.

## Запуск локально

Требуется Node.js 20 или новее.

```bash
npm install
cp .env.example .env
npm run dev
```

Откройте `http://localhost:5173`.

Проверки перед отправкой:

```bash
npm run lint
npm run build
```

## Деплой на Vercel

1. Импортируйте репозиторий в Vercel.
2. Framework Preset: **Vite**.
3. Build Command: `npm run build`.
4. Output Directory: `dist`.
5. Добавьте переменные окружения:

```text
SESSION_SECRET=<длинная случайная строка от 32 байт>
ALLOWED_ORIGIN=https://ваш-домен.vercel.app
AI_API_KEY=<ключ выбранного провайдера, если нужен живой ИИ>
AI_MODEL=gemini-2.5-flash
```

6. После публикации проверьте вход под Алексеем и Дмитрием в двух приватных окнах.
7. В комментарии к конкурсной работе укажите ссылку на сайт и тестовые аккаунты из таблицы выше.

Без `AI_API_KEY` кабинет продолжает работать: раздел ИИ показывает понятное сообщение о временной недоступности сервиса, а остальные сценарии остаются доступными.

## Структура проекта

```text
src/
  auth/                 клиентский API авторизации и типы
  components/           экраны кабинета и дизайн-система
api/
  _server.ts            cookie-сессии, шифрование и серверные seed-данные
  auth.ts               вход и выход
  student.ts            заявки, уведомления и состояние кабинета
  chat.ts               защищённый прокси к ИИ-провайдеру
server/dev-proxy.ts     локальный Express-адаптер Vercel API
```

## ИИ в процессе разработки

ИИ использовался для проектирования UX-сценариев, проверки требований конкурса, генерации React-компонентов, рефакторинга авторизации, code review, подготовки текстов интерфейса и составления конкурсного описания. Все изменения проверялись вручную, линтером, production-сборкой и API-сценариями входа, создания заявки и попытки открыть чужую заявку.
