# Цифровой деканат будущего МГИМО

Рабочий конкурсный прототип личного кабинета студента: расписание, БРС, заявки и справки, уведомления, цифровой студенческий билет и ИИ-ассистент. Интерфейс рассчитан на телефон от 360 px и сохраняет визуальное направление исходной версии проекта.

На сайте используются только вымышленные данные. Это концепт для конкурса, а не официальный сервис МГИМО.

Проверенные изменения: недельный обзор и экспорт .ics (МСК), общая PostgreSQL-защита входа, лимиты тела запроса, явная маркировка демо, обработка потери связи и ошибок интерфейса, production-сервер и Docker Compose с HTTPS, CI и новые тесты.

## Что можно показать жюри

- вход по корпоративной почте, СНИЛС или телефону;
- два независимых студенческих сценария: отличник и студент с академической задолженностью;
- расписание на неделю с переносами и аудиториями;
- оценки БРС и GPA, отдельные результаты сессии и даты пересдач;
- создание заявки на справку с отображением статуса;
- уведомления деканата и отметка прочтения;
- ИИ-ассистент с предложением действия, например оформления справки;
- профиль с цифровым пропуском и маскированием персональных данных;
- студенческий помощник с приоритетами, недельным планом и переключателем RU/EN.

Подробности обновления сценариев, прав, PDF и консультаций: [docs/PORTAL_UPGRADE_006.md](docs/PORTAL_UPGRADE_006.md).

## Архитектура безопасности и хранения

- `POST /api/auth` проверяет логин и пароль на сервере.
- Пароли сравниваются через `scrypt` с постоянным временем сравнения.
- После входа сервер выдаёт подписанную сессию в `HttpOnly`, `SameSite=Lax` cookie. В продакшене cookie получает флаг `Secure`.
- Профиль, расписание, оценки, заявки и уведомления выбираются по идентификатору из серверной сессии.
- Состояние заявок, уведомлений и чата хранится по `owner_id` в PostgreSQL, заданной через секретный `DATABASE_URL`; миграция находится в `migrations/001_student_state.sql`.
- В локальной разработке без `DATABASE_URL` используется только непостоянный memory adapter. В production `DATABASE_URL` обязателен.
- Оптимистическая блокировка версии предотвращает перезапись более новых данных; конфликт сохраняется повторно с объединением записей.
- `/api/chat` больше не принимает профиль студента от браузера: сервер сам получает текущий аккаунт из сессии и передаёт ассистенту только учебный контекст.
- Ключи задаются переменными окружения и не попадают в репозиторий.
- Vercel получает защитные заголовки: CSP, `X-Frame-Options`, `nosniff`, политика Referrer и Permissions Policy.

Прототип показывает безопасный пользовательский сценарий для конкурса. Для промышленного запуска нужны отдельные production-настройки PostgreSQL, полноценный реестр и область доступа сотрудников, аудит и отдельный канал доставки второго фактора.

## Запуск локально

Требуется Node.js 22.12 или новее (проверено также на Node.js 24).

```bash
npm ci
cp .env.example .env
npm run dev
```

Откройте `http://localhost:5173`.

Проверки перед отправкой:

```bash
npm run lint
npm run typecheck:api
npm run build
node --import tsx tests/state-isolation.mts
```

## Деплой на Vercel

1. Создайте отдельную тестовую PostgreSQL базу и выполните последовательно все `migrations/001…003` только в ней.
2. Импортируйте репозиторий в Vercel и добавьте секретные переменные окружения:

```text
DATABASE_URL=<pooled TLS connection string тестовой или production базы>
SESSION_SECRET=<длинная случайная строка от 32 байт>
ALLOWED_ORIGIN=https://ваш-домен.vercel.app
AI_API_KEY=<ключ выбранного провайдера, если нужен живой ИИ>
AI_MODEL=gemini-3.5-flash-lite
```

3. Framework Preset: **Vite**, Build Command: `npm run build`, Output Directory: `dist`.
4. Выполните Redeploy после изменения переменных.
5. Отдельно проверьте вход под двумя демонстрационными аккаунтами и изолированность заявок.

Без `AI_API_KEY` кабинет продолжает работать: раздел ИИ показывает понятное сообщение о временной недоступности сервиса, а остальные сценарии остаются доступными. Без `DATABASE_URL` локальный memory adapter теряет данные при перезапуске; это не доказательство production-готовности.

## Проверка и ограничения

`npm test` проверяет API, конфликты сохранения, изоляцию аккаунтов, очередь браузера и обработку ошибок ИИ. ИИ в тестах подменён. `npm run test:browser` проходит браузерные сценарии на 360/430/1280 px. Для PostgreSQL используйте отдельную тестовую базу и все три миграции; `npm run test:ai:shared` проверяет общий слот в двух Node-процессах.

Общая очередь и лимиты ИИ в production хранятся в PostgreSQL, а локально без базы — в памяти. Локальный PostgreSQL и браузер проверены в пакете 005; доступ к конкретной Neon и живой Gemini требуют проверки вашего окружения. Очередь не увеличивает квоту провайдера.

Настройка и команды: [docs/UPGRADE_SETUP.md](docs/UPGRADE_SETUP.md).

## Структура проекта

```text
src/
  auth/                 клиентский API авторизации и типы
  components/           экраны кабинета и дизайн-система
api/
  _server.ts            сессии, owner-scoped storage adapter и API-утилиты
  auth.ts               вход и выход
  student.ts            заявки, уведомления и состояние кабинета
  chat.ts               защищённый прокси к ИИ-провайдеру
server/
  stateStore.ts         PostgreSQL/memory storage с optimistic locking
  dev-proxy.ts          локальный Express-адаптер Vercel API
migrations/
  001_student_state.sql Student storage
  002_ai_runtime.sql    Shared AI limits and leases
```

## ИИ в процессе разработки

ИИ использовался для проектирования UX-сценариев, проверки требований конкурса, генерации React-компонентов, рефакторинга авторизации, code review, подготовки текстов интерфейса и составления конкурсного описания. Проведённые проверки перечисляются только в отчёте конкретного изменения; живой Gemini не заявляется без безопасно настроенного ключа.

Актуальная архитектура использует PostgreSQL по `DATABASE_URL` вместо cookie состояния. Подробности и ограничения: `docs/UPGRADE_SETUP.md`.
